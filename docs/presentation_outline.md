## Capstone 다중 CCTV 추적 파이프라인 발표 스크립트

### 1. 서론 (약 1분)
이번 프로젝트는 여러 대의 CCTV에서 들어오는 실시간 영상에서 특정 차량을 선택하고, 카메라를 옮겨 가더라도 같은 차량으로 인식해 추적을 이어 가는 시스템입니다. 기존 관제센터에서는 화면을 바꿀 때마다 동일 차량인지 다시 검증해야 해서 시간이 많이 들었는데, 우리는 GPU 기반 YOLO11 추적과 Re-ID를 결합해 이 과정을 자동화했습니다. 실제 HLS 스트림을 API로 받아와 처리하며, 웹 UI를 통해 원격으로 클릭과 키 입력까지 전달할 수 있어 현장에서도 바로 사용할 수 있는 형태를 목표로 했습니다.

### 2. 시스템 구조 (약 2분)
먼저 입력 단계에서는 `HLSStreamManager`가 ITS API로부터 HLS URL을 주기적으로 갱신하면서 좌·중·우 카메라를 `SwitchController`에 연결합니다. URL이 만료되거나 끊길 때는 자동으로 재시도하고, 좌우 카메라를 준비해 두었다가 tri 모드로 전환하면 즉시 화면을 띄웁니다.  
이후 추적 단계에서는 `detectors/YOLOTracker`가 Ultralytics YOLO11의 `model.track()` 기능을 활용해 한 번의 GPU 연산으로 탐지와 ByteTrack 추적을 동시에 수행합니다. 단일 모드에서는 중앙 카메라만 처리해 HUD에 경계 박스를 표시하고, tri 모드에서는 좌·중·우 프레임을 720×480 크기로 맞춰 가로로 붙인 뒤 각 세그먼트에 독립적인 YOLOTracker를 돌립니다.  
사용자가 특정 차량을 클릭하면 `SelectionHandler`가 좌표를 실제 프레임으로 환산해 가장 가까운 트랙을 찾아 `tracker.selected_id`에 기록합니다. 여기에 과거 히스토리 버퍼를 동시에 조회해 현재 프레임에 박스가 없더라도 최근 15프레임 안에서 위치가 가까운 차량을 찾아낼 수 있습니다. 선택 즉시 Re-ID 갤러리에 crop을 채우고, 웹 대시보드와 키/클릭 이벤트도 동기화됩니다.  
핵심인 Re-ID 및 handover 단계에서는 `ReIDBank`가 선택된 차량의 crop을 최대 다섯 장까지 수집하고, 각 장의 5개 밴드를 기반으로 Bhattacharyya distance를 계산합니다. tri 모드에서 또 다른 카메라에 동일 차량이 나타나면 `avg_bhatta_to_box_banded5_improved`로 거리를 측정하고, `ConsecutiveMatchValidator`가 연속 세 번 임계값을 통과했을 때만 동일 차량으로 인정합니다. 그 순간 remap 테이블을 갱신해 새 카메라에서도 같은 ID로 표시하고, `log_vehicle_tracking`에 이벤트를 남깁니다.  
UI와 웹 부분에서는 OpenCV HUD가 선택 차량을 신뢰도 기반의 붉은색 농도로 표시해 직관적으로 상태를 알 수 있고, Flask 대시보드가 `/api/key`, `/api/click`, `/api/clear_selection` 등을 통해 원격 제어를 지원합니다. 통계와 로그는 SQLite 및 `tracking_logs`, `reid_logs_5band`에 저장되어 사후 분석도 가능합니다.

### 3. 주요 기술적 특징 (약 1.5분)
이 시스템의 장점은 여러 요소가 조합된 데 있습니다.  
첫째, YOLO11과 ByteTrack을 통합해 GPU 가속으로 추적을 수행하므로 한 대의 GPU로도 10~15 FPS 수준의 실시간 처리가 가능합니다. 좌·중·우 세그먼트에 각각 YOLOTracker를 할당해 화면 합성 후에도 지연을 최소화했습니다.  
둘째, Re-ID를 단순히 단일 특징이 아니라 5개 밴드로 분리해 저장하고, 각 밴드의 Bhattacharyya distance를 기록합니다. 덕분에 조명이나 각도가 달라져도 평균 거리 외에 밴드별 패턴을 분석할 수 있어 handover 정확도가 올라갑니다.  
셋째, Adaptive threshold와 연속 검증 로직을 도입했습니다. 같은 카메라에서의 비교와 다른 카메라 간 비교에 서로 다른 임계값을 적용하고, 세 번 연속 기준을 만족해야만 선택 ID를 갱신하기 때문에 오탐 가능성이 크게 줄었습니다.  
넷째, tri-prepare 모드에서는 좌→중→우 순으로 ReID 갤러리를 채우고, remap 구조를 이용해 실제 트래커가 제공하는 ID와 UI에 보여주는 ID를 분리합니다. 이 덕분에 handover 직후에도 선택한 차량이 붉은 박스로 이어져 오퍼레이터가 차분하게 추적할 수 있습니다.  
마지막으로, Flask 웹 인터페이스를 통해 원격에서도 키 입력과 클릭을 전달하고, 선택 ID·FPS 등을 모니터링할 수 있습니다. `web_util`이 OpenCV 창과 웹 서버를 연결해 키 입력을 공유하고, 로그/크롭 저장 기능(CropSaver, tracking_logs)이 있어 운영 중 발생한 이벤트를 나중에 재생산할 수 있습니다.

### 4. 성과와 향후 계획 (약 0.5분)
이 파이프라인을 GPU 장비에서 돌렸을 때 단일 모드 기준 13~15 FPS, tri 모드에서도 실시간에 가까운 성능을 확인했습니다. 선택·handover 이벤트가 모두 로그로 남기 때문에 같은 차량을 다른 카메라에서 어떻게 이어받았는지 증빙 자료로 활용할 수 있습니다. 다만 HLS 네트워크 품질이나 CUDA 설치 여부에 따라 성능 편차가 발생할 수 있으므로, 장비 세팅을 정확히 맞추는 것이 중요합니다. 앞으로는 더 많은 카메라를 동시에 처리하거나, 딥 Re-ID 모델을 추가해 5-band 방식과 앙상블을 구성하는 방안을 고려하고 있습니다. 또한 웹 UI에 거리 로그 시각화나 자동 알림을 넣어 실무 배치를 준비할 계획입니다.  

(*발표 코멘트용*) 지도 연동 및 속도/검문소 분석 확장: 카메라 위치 메타데이터를 추가하고 ReID 로그의 시간차를 활용하면, 차량이 카메라 A→B→C로 이동한 속도를 추정해 지도 위에 표시하거나, 정체 구간·검문소 후보 위치 같은 의사결정 정보를 제공하는 방향으로 확장 가능합니다.
